# field-notes — находки, которые переживают проект

## Зачем это нужно

Грабли не привязаны к проекту. Флаг `--dry-run`, который сносит каталог; временная зона,
которая молча резолвится в UTC; скриншот, приходящий раньше композитинга. Такое ловится
дорого — сорок минут диагностики, две ложные гипотезы, — и стоит ровно столько же во второй
раз, если между заходами прошёл месяц и никто ничего не записал.

Заметка окупается не в момент написания, а в момент **узнавания**: через полгода в другом
репозитории появляется похожий симптом, и вместо новой диагностики нужен один поиск.
Поэтому у заметки два адресата — человек, который читает индекс глазами, и агент, который ищет
по нему текстом. Заголовок — утверждение, а не тема; в тексте — те слова, которыми симптом будет
описан в следующий раз (точная формулировка ошибки, имя флага, имя инструмента).

Хранилище общее для всех агентов на машине: Claude Code и Codex пишут и читают одни и те же
файлы. Ценность именно в этом — находка одного становится доступна другому.

## Где лежат заметки и чем с ними работать

Корень: `$FIELD_NOTES_DIR` → `~/.claude/field-notes` (если есть) → `~/.codex/field-notes` (если
есть) → создаётся `~/.claude/field-notes`. Внутри `INDEX.md` и `notes/YYYY-MM-DD-slug.md`.
Не заводи второй корень «для этого проекта»: смысл в том, что хранилище одно. Проектные знания
(«как деплоится этот сервис») живут в репозитории проекта, а не здесь.

Все команды — через `scripts/fn.sh` из папки этого скилла (`<skill>` ниже — она):

```bash
sh <skill>/scripts/fn.sh search <слова…>     # поиск с ранжированием — начинай с него
sh <skill>/scripts/fn.sh grep '<строка>'      # сырой поиск точной строки ошибки
sh <skill>/scripts/fn.sh new <slug> --title "…" --area "…"
sh <skill>/scripts/fn.sh index               # пересобрать INDEX.md после правки заметок
sh <skill>/scripts/fn.sh lint                # проверить хранилище — после каждой записи
sh <skill>/scripts/fn.sh touch <id> [--status …] [--upstream URL]
sh <skill>/scripts/fn.sh issue-draft <id>    # черновик issue автору инструмента
sh <skill>/scripts/fn.sh list | root | init
```

`fn.sh` сам находит Python ≥3.9 (`$FIELD_NOTES_PYTHON` → `py -3` → `python3` → `python`). Без
Python работают только `root`, `init`, `new`, `grep`, `list` — тогда строку индекса добавь руками.
Флаги `--read-only` (ничего не пишет) и `--json` (вывод для машины) есть у всех команд.

**`INDEX.md` руками не правят** — его собирает `index` из frontmatter заметок; текст над маркером
`<!-- fieldnotes:index … -->` ручной и сохраняется. Поэтому несколько агентов могут писать
одновременно: каждый правит свою заметку, таблица собирается заново под блокировкой.

## Режим 1. Прочитать — перед тем как чинить

Половина ценности скилла, и её обычно пропускают. Прежде чем разбираться с проблемой, чей
симптом вызывает ощущение «где-то я это видел», потрать один вызов:

```bash
sh <skill>/scripts/fn.sh search git bash часовой пояс
```

Ищи по симптому и по имени инструмента, а не по своей гипотезе о причине — гипотеза может быть
той самой, которую прошлый заход уже опроверг. `search` требует совпадения всех слов и ставит
выше совпадения в заголовке; синонимов он не знает — не нашлось, попробуй другие слова или
`grep` по точному тексту ошибки. Нашлось — прочитай заметку целиком: в разделе «что увело не
туда» обычно лежит та дорога, на которую ты собирался свернуть.

Отдельный повод заглянуть — когда инструмент дал **отрицательный** результат: `grep` ничего не
нашёл, в логе нет ошибок, на скриншоте пусто. Отрицательный результат одинаково хорошо
объясняется и отсутствием дефекта, и сбоем канала измерения; такие случаи копятся быстрее всего.

## Режим 2. Записать

Пиши в той же сессии, пока живы детали: точная команда, точный вывод, что проверял до этого.
Через день останется пересказ, а пересказ не лечит — лечит воспроизводимая проверка.

**Стоит заметки**, если выполнено хоть что-то из:

- root cause оказался не тем, чем выглядел симптом;
- инструмент соврал молча — вернул код 0, правдоподобное значение, пустой результат вместо ошибки;
- фикс, который выглядел очевидным, сломал что-то рядом;
- поведение зависит от версии или платформы, то есть на соседней машине не воспроизведётся;
- на диагностику ушло заметно больше времени, чем на саму починку.

**Не стоит заметки**: обычная ошибка в своём коде, которую нашли и починили; то, что дословно
написано в документации инструмента первым абзацем; разовая частность проекта (это в `HANDOFF.md`
или README проекта); «на будущее надо бы» без случившегося факта.

Порядок:

1. `fn.sh new <slug> --title "<утверждение>" --area "<инструмент / область>"` — дату ставит сам
   (из системы, не из головы). Если есть похожие заметки, он остановится и покажет их: тогда это
   **обновление** (режим 3), а не новая заметка; `--force` — только если точно другой механизм.
2. Заполни frontmatter и разделы. Поля — в [`references/note-format.md`](references/note-format.md);
   главное: `summary` — одна плотная строка для индекса (механизм, цифры, признак узнавания:
   не «проблемы с таймзонами», а «`TZ=Asia/Bangkok` в Git Bash молча даёт UTC, промах 7 часов,
   код 0»), `tool_version` — версия, на которой проявилось, `upstream` — ссылка на issue, если
   есть. Разделы, где писать нечего, убери: пустой заголовок читается как «не проверяли».
3. `fn.sh index`, затем `fn.sh lint` — ноль ошибок. lint ловит забытый индекс, заглушки шаблона,
   неизвестный статус, битые ссылки и то, что похоже на секрет.

Разделы тела: Контекст · Симптом (дословно) · Root cause (механизм, или честное «не найден») ·
Фикс / workaround (копипастой) · Как проверить (наблюдаемый эффект, а не наличие правки:
«тег есть в сборке» ≠ «функция появилась в window») · Что увело не туда (самый ценный раздел и
единственный, который нельзя восстановить позже) · Caveats · Критерий превращения в скилл.

## Режим 3. Обновить, а не размножить

Та же грабля во второй раз — **обновление существующей заметки**. Два разбора одного механизма
в разных файлах означают, что в следующий раз найдётся только один, и скорее всего не тот.

Добавь в заметку блок `## Обновление DD.MM: <что нового>` — новый случай, чем отличался, какая
часть прежнего вывода не сработала; допиши `summary`; затем `fn.sh touch <id>` (ставит `updated`
и пересобирает индекс) и `fn.sh lint`.

Особенно важен случай, когда повтор произошёл **у того, кто правило знал**. Это не «забыл» — это
значит, что правило невыполнимо на практике, и в обновлении нужен не повтор правила, а вывод,
почему оно не сработало и что должно встать на его место.

## Статусы и жизнь после записи

`active` — грабля актуальна · `workaround` — есть локальный фикс или обход · `needs-verification`
— гипотеза, не доказано (lint напомнит через 30 дней) · `fixed-upstream` — починили у автора
инструмента (нужна ссылка `upstream`) · `obsolete` — неактуально (инструмент ушёл, версия
другая) · `promoted` — стала скиллом. Смена статуса: `fn.sh touch <id> --status <статус>`.

Заметка не удаляется ни в каком статусе: даже `obsolete` хранит, почему было именно так.

## Отнести автору инструмента

Многие грабли — баги чужих инструментов. Пока они не исправлены у автора, обход живёт в каждой
сессии; сообщить — способ, которым грабля умирает естественно.

1. Поищи в трекере инструмента по симптому: дополнить чужой issue лучше, чем открыть дубль.
2. `fn.sh issue-draft <id>` печатает черновик: заголовок, версия, контекст, симптом, root cause,
   как воспроизвести, обход. Маска убирает очевидное — ключи и токены, PEM-блоки целиком,
   домашние пути (`C:\Users\…`, `/c/Users/…`, `/home/…`), IPv4, email, chat id `-100…`. Имена
   людей, внутренние хосты, IPv6 и секреты необычного вида она **не** ловит: прочитай каждую
   строку вместе с пользователем. Для англоязычного трекера переведи.
3. Публикует пользователь — это внешнее действие. Ссылку потом в заметку:
   `fn.sh touch <id> --upstream <URL>`; индекс покажет `owner/repo#N`.
4. Починили — `fn.sh touch <id> --status fixed-upstream`, в заметке — с какой версии.

## Когда заметка становится скиллом

Заметка описывает случай, скилл — процедуру. Переводить стоит, когда набралось: повторяемость
(три и больше случаев одного класса), проверяемая последовательность действий и ценность в
момент, когда агент ещё не знает, что попал в этот класс — то есть нужна автоматическая
активация по описанию, а не поиск по индексу. Тогда заведи скилл, у заметки — `status: promoted`
и `candidate_skill: <имя>`. Заметку не удаляй: скилл говорит, что делать, заметка хранит, почему
именно так, и через полгода второе ценнее первого.

## Гигиена

Секреты, токены, пароли, персональные данные клиентов — не переносить: в заметке место
маскированному хвосту и указанию, где ключ лежит. Из проектных подробностей оставлять только то,
без чего находка непонятна: заметка должна читаться человеком, который этот проект не видел.
Хранилище старого формата (строка `**Date:** · **Area:** · **Status:**` и индекс, который вели
руками) переводится командой `fn.sh migrate --from <root>` — сначала без `--apply`, и с бэкапом.
